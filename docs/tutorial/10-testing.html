Chapter 10 · Evidence

如何证明“算对了”和“真的更快”

推理系统最容易犯的错误，是把“能运行”当成“正确”，把“一次更快”当成“有性能结论”。这个项目把证据分成不同层级，并保存原始条件。

1. 四层正确性金字塔

Level 1

数学

Q/K/V、RoPE、RMSNorm、MLP 中间 tensor 与 HF 逐检查点对拍。

Level 2

状态

Cache 增长、失败回滚、block 复用、double-free、row 顺序。

Level 3

Kernel

CUDA 与 Python reference/连续 Attention 对拍多长度、多块、GQA。

Level 4

端到端

Continuous Engine 每请求完整 greedy tokens 与 HF oracle exact match。

2. 为什么 HF baseline 不用 generate()

transformers.generate() 内部包含采样、停止、Cache、beam 等复杂控制逻辑，不适合作为每一步可观察的 oracle。项目显式调用：

prefill(input_ids, attention_mask)
→ 取最后位置 logits
→ argmax 得到 token
→ decode_one(token, past_key_values)
→ 重复

这样每一步 logits、token 和 Cache 都能单独与自有 Runner 对拍。

3. 单元测试为什么尽量不用真实大模型

快速测试使用小 tensor、fake causal LM 或 monkeypatch reference，避免网络、下载和 GPU 环境让状态机测试变慢/不稳定。真实 Qwen correctness 由独立 CLI gate 执行。

测试类型回答的问题例子
纯 CPU unit test状态、shape、异常是否正确Scheduler FIFO、allocator double-free
CUDA parameterizedkernel 数值与边界变长、非连续 block、GQA
真实模型 experiment完整 Qwen 是否与 HF 一致逐层 logits、最终 tokens
release gate同一 clean commit 是否整体通过182 passed + correctness + benchmark

4. 请求级指标的严格定义

queue_wait = first_prefill_start − arrival
TTFT = first_token_ready − arrival
TPOT[i] = token[i+1]_ready − token[i]_ready
E2E = last_token_ready − arrival
post_token = completed − last_token_ready
i

只有一个输出 token 的请求没有相邻 token，因此 TPOT 是 None，不是 0。填 0 会让短请求虚假拉低总体 TPOT。

同一个 Engine step 的多个请求共享一次 D2H，它们的 ready_ns 可以相同。这代表控制面真正同时看到这些 token。

5. Benchmark 纪律

  • 先 warmup，排除首次 JIT/缓存影响
  • 保存所有 raw samples，不只写一个平均值
  • 用 median，并说明 percentile 算法
  • 对照 case 每轮交错，奇偶轮反转执行顺序
  • 记录 GPU、驱动、CUDA、PyTorch、Python 和 Git commit
  • 记录 peak memory、功耗/频率漂移边界
  • Correctness 必须先通过，再接受性能样本

kernel 微秒级 benchmark 使用 CUDA Event 包围多次 launch，再除以 iteration 数；端到端 TTFT/E2E 使用 CPU 单调时钟，因为它要覆盖排队和控制面。

不能把这些数字外推到其他模型、GPU、prompt 分布或在线 arrival。它们只证明这个固定实验条件下的行为。

7. Mixed Prefill Budget 的负结果也有价值

同一份 v1.0.0 release candidate evidence 中，项目尝试限制 mixed step 新接纳的 Prefill tokens，希望减轻 TPOT 干扰。budget=4 让 TPOT median 改善 5.28%，却使吞吐下降 8.75%、TTFT p95 上升 25.91%、E2E p95 上升 15.02%。这些数字也不是 v1.1.0 的新 benchmark。

因此这个旋钮保留在代码里作为教学实验，但默认关闭、不作为推荐策略。好的工程记录不仅保存成功优化，也保存被数据否决的方向。

检查：为什么 profiler 数据不能直接当端到端性能数据？
Profiler 往往只采一个 kernel 或有限时间窗，且采集本身有开销。它用于解释 occupancy、memory access、stall 或 host 时序；TTFT/TPOT/E2E 则需要完整 workload、多轮 raw samples 和明确的用户可见边界。

Chapter 06 · Paged KV

把连续 Cache 拆成可复用的物理块

Paged KV 的核心不是“把 tensor 切小”这么简单，而是分离逻辑 token 顺序与物理显存位置，并让 allocator、request table、storage 和 transaction 各自守住职责。

1. 连续预留为什么浪费

如果每个请求都预留最大长度 2048，但大多数只用几十个 token，显存会被空槽占住。分页策略用固定大小 block，按请求实际需要分配。

连续预留

每请求一大段

Request A · capacity 12
A0A1····

请求结束前，未用空间也不能给别人。

Paged

按 block 组合

block 2
A0A1·
block 4
B0B1B2

请求只持有所需块，结束后整块复用。

2. 三层数据结构

FixedBlockAllocator只管理整数 block ID：free list + allocated set；不持有 tensor。
RequestBlockTable保存某请求的逻辑 block → 物理 block 映射，以及 token_count/pending。
PagedKVStorage真正预分配 GPU K/V tensor，并按 table 提供的地址写入。
PagedKVCacheManager统一拥有以上对象和 request registry，对 Scheduler/Engine 提供稳定 API。
storage shape = [layer, physical_block, kv_head, block_offset, head_dim]

3. 逻辑 token 如何找到物理地址

设 block_size=3，请求 A 的 block table 为 [2,0,5]。

logical_block = token_index // block_size
block_offset = token_index % block_size
physical_block = block_table[logical_block]
查 token 4

4 // 3 = 1，所以查 table[1]，得到 physical block 0；4 % 3 = 1，所以在 block 0 的 offset 1。

physical 0
t3t4t5
physical 1
···
physical 2
t0t1t2
physical 5
t6t7·

逻辑上 token 2→3 连续，物理上却从 block 2 跳到 block 0。Paged Attention 的职责就是按 table 保持正确逻辑顺序。

4. Allocator 如何保证原子分配

def allocate(self, block_count):
    if block_count > self.free_count:
        raise BlockPoolExhaustedError(...)
    block_ids = tuple(self._free_block_ids.pop()
                      for _ in range(block_count))
    self._allocated_block_ids.update(block_ids)
    return block_ids

先检查容量，再 pop，所以 OOM 时 free list 完全不变。释放也先验证所有 ID 合法、没有重复且确实 allocated，之后才批量修改，避免“释放一半后报错”。

5. RequestBlockTable 的增长事务

计算新 token_count

new = current + append，据此向上取整需要多少 blocks。

只申请差额

additional = required_blocks - current_blocks。块内还有余量时不会分配。

记录 new_block_ids

pending 保存本次新申请的后缀。abort 时只释放它们，不动历史 blocks。

commit token_count

成功后才把 pending.end 设为正式 token_count。

跨块增长

block_size=3，当前 token_count=3，已有 block [2]。append 1 后需要 2 个块，新申请 [0]，table 变 [2,0]，pending=[3,4)。若失败，abort 删除后缀 [0] 并归还 allocator，table 回到 [2]。

6. Storage 如何写跨块 token

for relative_index in range(pending.token_count):
    logical_index = pending.start + relative_index
    location = table.locate(logical_index, include_pending=True)
    self.key[layer, location.block_id, :, location.block_offset, :].copy_(
        key[:, relative_index, :]
    )

实现为清晰而逐 token copy，主要用来固定地址语义。Decode CUDA kernel 的读取则直接在设备端做相同的整数映射，不先 gather。

7. Batch Metadata 为什么要 padding

GPU tensor 必须是矩形，但请求 block 数不同。假设：

A: blocks [2, 4, 5], length 7
B: blocks [0, 6],    length 4
C: blocks [1, 3],    length 6

block_table = [[2,4,5],
               [0,6,-1],
               [1,3,-1]]
sequence_lengths = [7,4,6]

-1 只是 padding，kernel 必须用 sequence length 算出真正要读的 block 数，不能扫描整行宽度。完整生命周期预留时，行尾也可能是合法但尚未使用的未来 blocks，仍不能提前读取。

8. 当前 Admission 为什么保守预留全部 blocks

PagedBlockAdmissionController 在接纳请求时按 prompt + max_new − 1 一次预留，保证 Decode 中途不会 OOM。代价是并发数比按需增长更保守。

required_blocks = ceil(max_cache_tokens / block_size)
↔

这是没有 preemption 时的正确性/利用率取舍。真正的生产引擎可以按需增长，在压力下抢占或换出请求；本项目明确没有实现这些机制。

检查：为什么 GPU storage 初始化时已经分配全部 blocks，admission 还要“分配 block”？
GPU tensor 的总物理池已经存在；allocator 分配的是这些槽位的所有权 ID。它不再次申请 CUDA memory，而是保证两个活跃请求不会写同一个物理 block。

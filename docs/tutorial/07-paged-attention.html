从 Python Reference 到 CUDA Kernel

先用最清晰的 Python 实现定义“正确答案”，再让 CUDA 保持相同的地址映射和数学语义。理解这一章的关键，是把逻辑 token 顺序、物理 block 地址和 softmax 三件事分开。

Reference 中的 Python loop、.item() GPU 同步和完整 score tensor 都很慢，但它们让逻辑一目了然。它是数值 oracle，不是 benchmark 对象。

3. CUDA v1 的线程映射

grid.x = batch × num_query_heads
block.x = 64 threads = head_dim
一个 CTA = 一个 (request, query_head)
B=3, Hq=14

总共 launch 42 个 CTA。CTA 0–13 属于 request 0，14–27 属于 request 1，28–41 属于 request 2。每个 CTA 的 64 个线程分别负责输出向量的一个维度。

const int query_head = blockIdx.x % num_query_heads;
const int batch_index = blockIdx.x / num_query_heads;
const int dim = threadIdx.x;

const int group_size = num_query_heads / num_kv_heads;
const int kv_head = query_head / group_size;

4. 每个历史 token 的地址计算

for (int token_index = 0;
     token_index < sequence_length;
     ++token_index) {
  logical_block = token_index / block_size;
  block_offset  = token_index % block_size;
  physical_block = block_table[
      batch_index * max_blocks + logical_block];

  cache_offset = (((physical_block * Hkv + kv_head)
                   * block_size + block_offset) * 64);
}

这段整数运算与上一章 RequestBlockTable.locate() 完全相同，只是从 Python CPU 元数据搬到了每个 CUDA CTA 内。

5. 64 线程如何算一个 Q·K

线程 dim 只乘 Q[dim]×K[dim]，把结果写进 shared memory，再做树形 reduction：

dot_products[dim] = query_value * key[cache_offset + dim];
__syncthreads();

for (int stride = 32; stride > 0; stride >>= 1) {
    if (dim < stride)
        dot_products[dim] += dot_products[dim + stride];
    __syncthreads();
}
score = dot_products[0] * scale;

第一次把 64 个值合成 32 个，接着 16、8、4、2、1。v1 使用 shared memory 和全 CTA 同步，清晰但不快；后续可单独替换为 warp shuffle。

6. Online Softmax：不保存完整 scores

普通 softmax 需要先看到所有 scores 才知道最大值和分母。Online 版本扫描一个 score 就更新一次状态：

new_max = max(running_max, score)
alpha = exp(running_max − new_max)
beta = exp(score − new_max)

running_sum = running_sum × alpha + beta
output_acc = output_acc × alpha + beta × V[token]
两步数值例子

第一个 score=2：max=2，sum=1，acc=V₀。

第二个 score=3：new_max=3，历史权重缩放为 exp(2−3)=0.3679；新 token 权重为 1。于是 sum=1.3679，acc=0.3679V₀+V₁。除以 sum 后与对 [2,3] 做普通 softmax 相同。

所有 running 状态和 V 累加使用 FP32，循环结束再转换到 FP16 输出。

8. v1 的限制与 split-KV 实验

v1 稳定路径

  • FP16
  • head_dim=64
  • query length=1
  • 一个 CTA 串行扫描全部 tokens
  • GQA/MQA 和变长 batch

没有进入稳定 dispatch

  • half2 / 向量化 load
  • warp reduction
  • token 并行
  • 自动选择 split-KV
  • 通用 head_dim/dtype

split-KV 实验把长序列拆给多个 CTA，再合并 online-softmax 状态。它在部分长序列可能有收益，但短序列的 partial/merge 开销明显，因此保留为实验而非自动 dispatch。

检查：为什么不能对每个物理 block 单独 softmax 后再把输出相加？
Softmax 分母必须覆盖整条逻辑序列。每块独立归一化会让每个块的概率都各自和为 1，改变块之间的相对权重。必须拼接 scores，或像 online softmax 一样正确合并 max/sum 状态。

先看最终答案：这个项目做什么？

用户给出一句话，例如“请解释 KV Cache”。Tokenizer 把文字变成 token ID；Engine 把请求交给 Scheduler；Scheduler 决定本轮哪些请求运行；ModelRunner 在 GPU 上执行 Qwen；KV Cache 保存历史注意力需要的 K/V；最后 logits 选出下一个 token。不断重复，直到 EOS 或达到生成上限。

项目定位：它不是生产版 vLLM 的复制品，而是一个教学型、单 GPU、同步、greedy 推理引擎。它把 vLLM 最关键的概念拆成可验证的小步骤。

学习时始终记住的四个问题

这一段代码属于控制面、计算面，还是存储面？

Scheduler 是控制面；ModelRunner/CUDA 是计算面；KV Cache Manager 是存储面；Engine 是编排层。

这个 tensor 的 shape 是什么？每个维度代表什么？

大多数模型 bug 都不是公式不会，而是 batch、head、sequence、head_dim 的顺序错了。

当前 token 已经“写入”，还是已经“可见”？

事务把物理写入和逻辑可见性分开；pending 数据只有 commit 后才成为正式历史。

这是正确性实现还是性能实现？

Python reference 可以慢但清晰；CUDA kernel 才承担热路径。不能拿 reference 的速度评价设计。

Scheduler：每一步到底算谁

Scheduler 是纯 CPU 控制面。它不执行模型、不持有 GPU tensor，也不释放显存；它只维护请求状态，并生成一个确定性的工作清单。

1. 请求状态机

WAITING等待接纳
→
RUNNING已 Prefill/持续 Decode
→
FINISHEDEOS / max tokens

RequestState 保存：

request_id
prompt_token_ids
max_new_tokens
eos_token_ids
arrival_index
status / prefilled / finish_reason
generated_token_ids

它的 max_cache_tokens 属性返回 prompt + max_new − 1，供 Admission 计算最大 block 数。

2. SchedulerBatch 的每一项

ScheduledRequest 只有 request ID、工作类型和本次输入 token IDs：

WorkKindinput_token_idstoken_cost
PREFILL整个 promptprompt length
DECODE上一步生成的最后 1 token1

Scheduler 不生成 GPU tensor。这一步由 Engine 完成，所以调度策略可以在没有 CUDA 的测试里运行。

3. schedule_step() 精确算法

检查 outstanding batch

上一次 schedule 后必须先 apply 或 abort，防止同一请求被重复送进 GPU。

冻结 running_at_step_start

Static policy 是否允许 refill，必须看 step 开始时是否已有 cohort。

先加入所有 running Decode

每个成本 1，Decode priority 降低已有请求的 TPOT 抖动。

算剩余 request slots

max_running_requests − len(running)。

按 FIFO 查看 waiting 队首

检查总 token budget、mixed prefill budget 和 Admission blocks。

产生 outstanding SchedulerBatch

保存 step index，在 apply 前禁止产生下一批。

batch token cost = running request count + Σ(admitted prompt lengths)

4. 一个具体调度例子

参数：max_running_requests=2，max_batch_tokens=5。A prompt 长 3、生成 3；B prompt 长 2、生成 2；C prompt 长 3、生成 2。

STEP 0
A PREFILL ·3B PREFILL ·2
STEP 1
A DECODE ·1B DECODE ·1
STEP 2
A DECODE ·1C PREFILL ·3
STEP 3
C DECODE ·1

假设 B 在 step 1 完成，step 2 就腾出一个 slot；Continuous policy 让 C 立即加入。总成本 1+3=4，没有超过 5。

5. strict FIFO 与 whole Prefill

队首 A 长 5，后面 B 长 1，但本 step 只剩 3 token budget

Scheduler 停止接纳，不能跳过 A 选择 B。因为它不支持 chunked prefill，也选择 strict FIFO 保证到达顺序公平。

优点是行为简单、可复现；缺点是长 prompt 造成 head-of-line blocking。

i

别把 token budget 当成 KV block budget：已分配 block 的尾部空位只属于原请求，不能给新请求。只读单步估算器可检查给定下一轮的 block 缺口，但无法保证剩余整个生成期都安全，因此稳定 Admission 仍预留全生命周期容量。推导见容量分析。

6. Continuous 与 Static 的唯一区别

Continuous

每 step 可 refill

step 0: prefill A,B
step 1: decode A + prefill C
step 2: decode A,C
Static no-refill

等 cohort 排空

step 0: prefill A,B
step 1: decode A       # C 等待
step 2: decode A
step 3: prefill C

Static 不是让已完成请求继续 padding compute；它只是禁止向未排空的 running cohort 补新请求。这样实验只改变 admission policy。

8. abort_step() 如何让失败可重试

Decode 请求在 schedule 时没有改变生成结果；但新 Prefill 请求已经从 waiting 移到 running。失败时：

  • 检查它们还没有 prefilled/生成 token；
  • 状态改回 WAITING；
  • 从 running 删除；
  • 按逆序 appendleft，恢复到 waiting 队首且保持 FIFO；
  • step index 回退，重试沿用同一编号。
检查：为什么 Scheduler 自己不直接释放 blocks？
Scheduler 是纯逻辑状态机，不拥有 GPU storage。它只返回 finished_request_ids；Engine/Admission Controller 才知道并操作 Cache Manager。这样调度策略与存储实现解耦。

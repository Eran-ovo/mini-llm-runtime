2. 四个核心角色 + 一个编排者

RequestState保存 prompt IDs、生成上限、状态、已生成 token；不持有 GPU K/V。
RequestScheduler维护 waiting/running/finished，决定本 step 做哪些 Prefill/Decode。
QwenPrefillRunner只做模型数学：Embedding → 24 层 Decoder → LM Head。
PagedKVCacheManager拥有物理 block pool、GPU K/V tensors 和 request block tables。
ContinuousBatchEngine把上面三个组件按安全顺序串起来，转换 ID/tensor、同步 token、回滚和释放。

3. 一条完整请求的数据流

engine.submit()

登记到达时间，并把 token IDs 交给 Scheduler，状态为 WAITING。

scheduler.schedule_step()

先给已有 running 请求安排 Decode，再用剩余 token/slot 接纳 whole Prefill。

admission.try_admit()

为新请求创建 block table，并保守预留整个生命周期的 blocks。

runner.prefill() / decode_batch()

执行 Qwen，逐层写 K/V；argmax 在 GPU 上选 token。

一次 GPU→CPU 同步

所有请求 token 按 Scheduler 原顺序拼接，一次性回到 CPU。

apply + release

更新请求状态；EOS/达到上限的请求释放全部 blocks。

4. 为什么项目按 v0.1 → v1.0 演进

阶段只解决一个问题避免混入的错误
v0.1HF 显式 Prefill/Decode oracle先确定“正确输出是什么”
v0.2独立权重加载与 ModelRunner隔离模型公式/权重映射
v0.3连续 KV Cache先验证历史不重算与事务
v0.4Paged 地址管理隔离逻辑/物理映射
v0.5CUDA Paged Attention最后才引入 kernel 地址与数值问题
v0.6Scheduler + Engine在单请求正确后引入多请求状态
v1.0clean-tree release evidence保证结果与代码版本可追溯
i

这是学习这个项目最重要的方法论：不要同时改模型数学、Cache 布局和 CUDA kernel。每次只改变一个变量，并与上一层 reference 对拍。

5. 当前明确边界

已经有

  • Qwen2.5-0.5B FP16 greedy
  • Paged KV + CUDA Attention
  • 多请求 batched Decode
  • 同步 Continuous Engine
  • Static/Continuous 对照
  • 请求级指标与 release gate

没有

  • Web API / OpenAI compatible server
  • 异步 CPU/GPU overlap
  • Chunked Prefill / preemption
  • 采样、量化、分布式
  • Speculative Decoding

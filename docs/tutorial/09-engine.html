Chapter 09 · Continuous Engine

Engine 如何把所有组件串成闭环

ContinuousBatchEngine 是整个项目的稳定顶层入口。它只有约两百行，却承担最容易出错的跨组件契约：顺序、事务、同步、结果归属和资源释放。

1. 构造时先验证静态布局

Engine 要求 Runner 使用 paged_cuda backend，并检查模型与 Cache storage 的：

num_layers
num_key_value_heads
head_dim
dtype
device

任一项不一致都提前报错。例如模型 K/V 有 2 heads，而 Cache 按 4 heads 分配，若不在构造时拒绝，后面写地址可能 shape 错误甚至越界。

2. submit() 同时做两件事

arrival_ns = clock_ns()
request = scheduler.submit(
    request_id,
    prompt_token_ids,
    max_new_tokens=max_new_tokens,
    eos_token_ids=eos_token_ids,
)
metrics.register_request(request_id, arrival_ns)

请求必须通过 Engine 提交，而不是直接调用 Scheduler，否则 metrics 不知道 arrival 时间，后续无法计算 queue wait 和 TTFT。

torch.cat(...).cpu().tolist()，而不是每请求 .item()。

4. Mixed Batch 为什么要拆开执行

SchedulerBatch 可以同时包含新请求 Prefill 和旧请求 Decode，但它们的输入形状与 attention 语义不同：

Prefill 子批Decode 子批
输入长度每请求不同，当前逐请求执行每请求恰好 1
maskcausal mask无需显式 mask
Cache空 Cache 初始化已有变长 Cache 追加
当前实现N 次 runner.prefill1 次 runner.decode_batch
!

这意味着 mixed step 中，新请求的长 Prefill 会先执行，已有请求的 Decode 要等待，形成 Prefill/Decode interference。Continuous 提升整体排队与吞吐，但可能拉长某个 TPOT interval。

5. PagedBatchDecodeAdapter 做了什么

它把多个独立 RequestBlockTable 包装成 ModelRunner 认识的“批量 Cache”。最重要的契约是 batch row 顺序。

request_ids = ("C", "A", "B")

row 0: token_C, position_C, K/V_C, table_C, length_C
row 1: token_A, position_A, K/V_A, table_A, length_A
row 2: token_B, position_B, K/V_B, table_B, length_B

如果某处偷偷按 request 创建顺序 A/B/C 构造 metadata，所有 tensor 的 shape 都合法，CUDA 也可能不报错，但不同用户上下文会串行——这是最危险的一类 silent corruption。

批量事务

begin_decode() 逐请求 begin append。若后面的请求分配失败，会逆序 abort 前面已经 begin 的请求。所有层写完后才统一 commit。

6. 为什么 Prefill 必须先于 Decode

当前排序是为了可重试语义：

try:
    run_all_new_prefills()       # 结果暂不 apply
    run_one_batched_decode()     # 内部自带 batch transaction
except Exception:
    admission.release_admitted(prefill_ids)
    scheduler.abort_step()
    raise

如果先成功提交旧请求 Decode，再执行新 Prefill，而 Prefill 随后失败，旧请求 Cache 已推进，Scheduler 却没 apply，无法原样重试。先 Prefill、最后事务式 Decode，可以在异常时让整个 step 回到开始前。

7. 一次 D2H 同步的意义

EOS/max tokens 判断发生在 CPU Scheduler，因此 token 必须回 CPU。逐请求调用 .item() 会造成 B 次 GPU 同步。Engine 先在 GPU 收集所有 argmax，最后只做一次：

ordered_gpu_tokens = torch.cat([
    selected_tokens[item.request_id]
    for item in batch.items
])
ordered_cpu_tokens = ordered_gpu_tokens.cpu().tolist()

这是每 step 的同步屏障。当前同步 Engine 不尝试用 stream/event 双缓冲隐藏它。

8. 请求指标在哪些边界记录

ARRIVAL
engine.submit
PREFILL
record_prefill_started
TOKEN READY
D2H 完成 · record_tokens
COMPLETED
apply + release 完成

用户可见 E2E 截止到最后 token ready，不把 block 清理混进去；清理时间单独叫 post-token completion。

9. NVTX 标记与 profiler 边界

enable_nvtx=True 时，Engine 为 schedule、整个 step、每个 Prefill、batched Decode、D2H 和 apply/release 推入 NVTX range。上下文管理器的 finally 确保异常也 pop。

检查：Engine 为什么不负责 tokenizer.decode()？
稳定 runtime 的输入输出契约是 token IDs。Tokenizer 属于模型边界/服务层，放在 Engine 内会把文本库、batch 编码和流式输出策略混入核心调度与执行逻辑。

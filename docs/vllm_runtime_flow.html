04 · Compute

Prefill 与 Decode

同一个 Decoder，两种完全不同的工作负载。Prefill 一次吞下整段 prompt；Decode 每个请求只推进一个 token，并复用此前的 KV。

每层先计算 Q/K/V 和 RoPE，再把 K/V 写入该请求的 pending slots。全部层成功后才 commit；最后位置 logits 经 argmax 直接产生第一个输出 token，所以首 token 不需要额外 Decode。

Next Logits[B,1,V]

不同请求可以有不同历史长度。当前 token 的 RoPE 位置是追加前长度；Attention 的可读长度是追加后长度。每一层只 launch 一次 batched Paged Attention，而不是每请求一次。

05 · Memory

Paged KV 怎么寻址

逻辑上每个请求的 token 连续；物理上它们可以散落在 GPU block pool。点击逻辑 token，观察两次除法如何落到真实物理槽位。

Request A · block_size = 3

逻辑 token

Request A 的 block table = [2, 0, 5]。因此逻辑相邻不要求物理相邻。

GPU physical block pool

物理块

完整 GPU storage
[layer, physical_block, kv_head, block_offset, head_dim]
单层 CUDA 输入
query [B,Hq,D] + K/V [blocks,Hkv,block_size,D]
批量地址元数据
block_table [B,max_blocks] + sequence_lengths [B]
↯

为什么需要事务？ 一次 token 会在所有 24 层写 K/V。若第 17 层失败，前 16 层已经写过的字节必须保持不可见；所以先 begin_append，全层成功才 commit，失败就 abort。

per-token loop

内核的 5 个动作

01
找到物理地址logical=t/block_size → physical=table[b,logical] → offset=t%block_size
02
GQA 选择 KV head多个 Query Heads 共享同一个 K/V Head。
03
计算 Q·K64 个线程各乘一个维度，再在 shared memory 做 reduction。
04
更新 online softmax只保存 running max / sum，不物化完整 score vector。
05
累加 Value对 V 做重标定后的加权累积，循环结束再除 running_sum。
numerical core

Online Softmax 为什么数值稳定

new_max = max(running_max, score)
alpha = exp(running_max - new_max)
beta  = exp(score - new_max)

running_sum = running_sum × alpha + beta
output_acc = output_acc × alpha + beta × V[t]
output = output_acc / running_sum

当新 score 抬高最大值时，历史权重整体乘 alpha 重新缩放，既避免溢出，也无需保存此前所有 score。累加使用 FP32，最终输出转换回 FP16。

07 · Scheduling

Continuous Batching

Batch 不是固定不变的。每个 step 都先保障正在生成的请求 Decode 一次，再用剩余 token budget 从 waiting 队首接纳完整 prompt。

当前 Engine 边界： ContinuousBatchEngine 已自动拆分 Prefill / Decode 子批、调用 Runner、统一同步 token、写回 Scheduler 并释放 blocks。当前仍是同步 Engine：Prefill 逐请求执行且位于 batched Decode 之前，不支持 chunked prefill、preemption 或 CPU/GPU overlap。

i

KV 容量边界：稳定 Admission 在接纳时预留整个生成期所需 block。独立的单步只读估算器可以根据活动请求、free block 与下一步 Decode/Prefill 计算缺口，但只能判断这一轮是否放得下，不能代替全生命周期的容量保证。原理见KV 预留容量分析。

scheduler decision order

schedule_step() 精确顺序

1
拒绝重入若上个 outstanding batch 尚未 apply/abort，禁止再次调度。
2
先放全部 running Decode每个请求成本恒为 1，保证活跃请求每 step 前进一步。
3
计算剩余 slot 与 token budgetbatch_tokens = Σ decode(1) + Σ admitted prompt length。
4
严格 FIFO 接纳 whole Prefill队首放不下就停止，不切 prompt，也不绕过它挑短请求。
5
Admission 原子预留 blocks资源不足时无副作用返回 False；请求继续 waiting。
controlled comparison

Continuous 与 Static 只差哪里

CONTINUOUS step 0 Prefill A, B step 1 Decode A + Prefill C ← 动态 refill step 2 Decode A, C STATIC (no-refill cohort) step 0 Prefill A, B step 1 Decode A ← C 等 cohort 排空 step 2 Decode A step 3 Prefill C

两种策略共用同一 Engine、Runner、KV Cache、Paged Attention 和 workload，只改变已有 cohort 未结束时能否补入新请求，因此性能差异主要来自 admission policy。

08 · Orchestration

Engine 一个 step

ContinuousBatchEngine 是把独立组件变成 runtime 的那层胶水。它不实现 Transformer，也不决定调度策略；它负责转换数据、确定调用顺序、同步结果和处理失败。

Engine
scheduler.schedule_step()

得到 mixed SchedulerBatch：items 保留逻辑顺序，同时暴露 prefill_request_ids / decode_request_ids。

Prefill
逐个执行新请求

构造 [1,S] input tensor，以 PagedRequestKVCache 写入已预留 blocks；GPU 上完成 argmax，但暂不回写 Scheduler。

Decode Batch
一次 decode_batch([B,1])

PagedBatchDecodeAdapter 保持 Scheduler 的 request 顺序，各层共享一份 block table / lengths metadata。

Engine
按 batch.items 原顺序重排 token

模型执行顺序是 Prefill→Decode，可能不同于 Scheduler items；必须按 request_id 恢复归属。

GPU → CPU
一次 .cpu().tolist() 同步

不逐请求 .item()；一个 step 的所有 greedy token 在一次 D2H barrier 后对控制面可见。

Scheduler
apply_step_results()

检查 ID 集合、追加 token、判断 EOS/max tokens、迁移 RUNNING→FINISHED。

Admission
release_finished()

释放完成请求 block table 的所有物理块，并记录 token ready / completion 指标。

why prefill first

为什么 mixed step 先 Prefill

新 Prefill 成功后结果仍未写回 Scheduler；旧请求 Decode 最后执行且自身有跨请求事务。若任意调用失败，可以释放本轮新 reservation，再让 Scheduler abort，整个 step 可原样重试。

try: run_each_prefill() run_one_batched_decode() except: admission.release_admitted(prefill_ids) scheduler.abort_step() raise
rollback invariants

失败后必须恢复什么

A
CacheDecode pending 全部 abort；Prefill reservation 全部释放。
B
队列本轮新接纳请求回 waiting 队首，保持原 arrival FIFO。
C
请求状态不得出现部分 generated tokens 或错误的 prefilled=True。
D
逻辑 step失败尝试不消耗 step_index，重试仍使用相同编号。

11 · Mental Model

必须守住的契约

理解这六条，基本就抓住了整个项目最容易出错、也最有价值的部分。

① Batch row 绝不能乱

token、position、Q/K/V、block table 和 length 的第 i 行必须属于同一 request。

② position ≠ read length

Decode position 是 old_len；当前 K/V 写入后 Attention 读取 old_len + 1。

③ 可见长度最后提交

24 层和 LM Head 都成功后才 commit；失败则所有请求一起回滚。

④ 最后输出不进 Cache

生成 N 个 token 最多只 Decode N−1 次，因此 capacity = prompt + N − 1。

⑤ Length 决定访问边界

block table 可能含 padding 或未来预留块，CUDA kernel 只能按 sequence length 访问。

⑥ Scheduler 不拥有显存

它只发完成事件；Engine/Admission Controller 才调用 manager 释放物理 blocks。
